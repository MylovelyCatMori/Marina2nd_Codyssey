기록된 예측은 "id는 고유값이라 중복 불가"였습니다. 규칙은 맞지만 **규칙을 위반했을 때 브라우저가 실제로 무엇을 하는지**는 답하지 않았습니다. 관찰한 뒤 아래 세 칸을 채우십시오.

| 질문 | 답 (2026-09-28) | 판정 |
|---|---|---|
| ① 콘솔에 에러가 났는가 | 에러 없음. `console.log` 두 줄만 출력 | ✅ |
| ② CSS는 두 요소 중 몇 개에 적용되었는가 | 둘 다 보라색. id 선택자는 고유성을 검사하지 않는다 | ✅ |
| ③ `querySelector`는 둘 중 어느 것을 골랐는가. 그 기준은 무엇이라고 보는가 | 첫 번째를 골랐다. 기준을 "먼저 선언된 것"이라 답함 | 🟨 절반 |

**③ 교정 · 기준은 원본 텍스트 순서가 아니라 현재 DOM 트리 순서다**

이 파일에서는 둘이 우연히 일치해서 구분이 되지 않았다. Console에서 두 번째 요소를 첫 번째 앞으로 옮긴 뒤 다시 조회해 확인했다.

```js
const list = document.querySelectorAll('#duplicated');
list[0].parentElement.insertBefore(list[1], list[0]);
console.log('[재확인] 순서 바꾼 뒤 :', document.querySelector('#duplicated').textContent);
```

결과: `[재확인] 순서 바꾼 뒤 : 두 번째 -- 같은 id 를 또 붙였다`

HTML 파일은 한 글자도 바뀌지 않았는데 결과가 달라졌다. 따라서 기준은 **작성 순서가 아니라 조회 시점의 트리 순서**다.

**미션 코드와의 연결**: `js/main.js`의 `els` 객체는 시작 시 한 번만 `querySelector`를 돌려 요소를 담아둔다. DOM이 다시 그려지면 담아둔 참조는 문서에서 떨어진 껍데기가 된다. 그래서 재시도 버튼(`js-retry`)과 필터 버튼(`js-filter`)은 요소에 직접 리스너를 달지 않고, 사라지지 않는 부모에 위임했다.

**추가로 배운 것**: id 중복은 HTML 규격 위반인데 브라우저는 에러를 내지 않는다. 잘못된 마크업을 만나면 멈추는 대신 최대한 해석해 계속 진행한다. 아무도 경고해주지 않으므로 위반이 조용히 남는다.

### 실험 3 · 오타 두 종류 (Console 확인)

| 콘솔 줄 | 기대값 | 실제값 | 판정 |
|---|---|---|---|
| `[실험3] D 배경` | `rgb(255, 165, 0)` (주황) | `rgb(255, 165, 0)` | ✅ |
| `[실험3] E 배경` | `rgba(0, 0, 0, 0)` (투명) | `rgba(0, 0, 0, 0)` | ✅ |
| `[실험3] F 배경` | `rgb(255, 165, 0)` (주황) | `rgb(255, 165, 0)` | ✅ |

E가 마지막 오답 지점입니다. 두 상자 모두 "앞 줄 orange + 뒤 줄 오류" 구조인데 결과가 갈립니다.
- D `blu`: **읽는 단계**에서 값이 아님이 드러나 그 줄이 버려집니다. 앞 줄 orange가 살아남습니다.
- E `var(--color-acent)`: 읽는 단계는 통과합니다. 문법상 정상이기 때문입니다. orange를 덮어쓴 **뒤** 계산 단계에서 변수를 못 찾아 실패하고, 최종적으로 투명이 됩니다.

추가 확인: Elements → Styles 패널에서 D의 `blu` 줄에는 **취소선**이, E의 줄에는 경고 아이콘이 붙는지 보십시오.

| 확인 항목 | 실제 화면 (2026-09-28) | 판정 |
|---|---|---|
| D의 `background-color: blu` 줄 표시 | **`blu` 값에만** 취소선 | ✅ |
| E의 `background-color: var(--color-acent)` 줄 표시 | 이 줄은 살아 있고, **앞 줄 `background-color: orange` 전체에** 취소선 | ✅ |

**이 관찰이 a4의 정답이다.** 취소선이 어느 줄에 그어졌는지가 두 오타의 차이를 그대로 보여준다.

- **D 값 오타**: `blu`는 색 이름이 아니므로 **읽는 단계**에서 선언이 버려진다. 버려졌으니 앞 줄 orange는 경쟁자가 없어 살아남는다. 그래서 orange에는 취소선이 없다.
- **E 변수 이름 오타**: `var(--color-acent)`는 문법상 정상이라 읽는 단계를 통과한다. 통과하는 순간 orange를 덮어쓴다(그래서 **orange에 취소선**). 그 뒤 계산 단계에서 변수를 못 찾아 실패하지만 orange는 이미 밀려나 돌아올 자리가 없다. 남는 것은 투명이다.

한 문장 요약: **값 오타는 실격이라 경기에 못 나가고, 변수 이름 오타는 출전해서 자리를 차지한 뒤 쓰러진다.**

실무 대응은 F 상자다. `var(--color-acent, orange)`처럼 두 번째 자리에 대체값을 두면 변수를 못 찾아도 orange로 떨어진다.
미션 코드에는 대체값을 쓰지 않았다. 변수를 전부 `:root`에 모아 선언했고, 오타가 나면 화면이 즉시 투명으로 깨져 바로 발견되기 때문이다.

### 미답 확인 질문 2개

관찰을 마친 뒤, **먼저 답을 쓰고** 직접 코드를 고쳐 확인하십시오. 순서를 지키는 것이 이 작업의 핵심입니다.

**질문 ①** `.swatch` 규칙 안에 `--color-accent: red;`를 한 줄 추가하면 A·B·C는 각각 무슨 색이 되는가. 그 상태에서 dark로 토글하면 어떻게 되는가.

> 예측 (2026-09-28): A·B·C 테두리 전부 빨강. dark 토글 후에도 테두리는 빨강 유지.
> 배경은 A·C 검정, **B 흰색**.
>
> 실제: 테두리 예측 전부 적중. 배경 A·C 어두움 적중. **B는 흰색이 아니라 연한 초록 `#eef7ee`.**
>
> 불일치 사유: B 자체는 배경이 없어 투명하고, 뒤에 있는 `.zone`의 배경이 보이는 것이다.
> `.zone { background-color: #eef7ee; }`는 **변수를 거치지 않은 리터럴**이라 테마 전환에서 빠진다.
> 테마 전환은 변수 값만 갈아끼우므로, 변수로 쓰지 않은 색은 그대로 남는다.
> **다크 모드가 어중간하게 깨지는 최다 원인이 이것이다.**

확인 방법 (Console, 파일 수정 없이):

```js
const s = document.createElement('style');
s.textContent = '.swatch { --color-accent: red; }';
document.head.append(s);
```

테두리 빨강 유지 ✅ · B 연한 초록 배경 ✅ 관찰 완료.

**정답 근거**: `.swatch`가 자기 자신에게 값을 선언했고, 탐색은 자신부터 시작해 처음 만난 곳에서 멈춘다.
`[data-theme="dark"]`는 `html`에 값을 심지만 그것은 경로의 맨 끝이라 도달하지 않는다.

**미션 코드 연결**: `css/style.css`는 색 자리에 리터럴을 한 번도 쓰지 않고 전부 `var(--color-*)`로 받았다.
그래서 `[data-theme="dark"]` 블록에서 변수만 바꾸면 전체가 따라온다.

**질문 ②** B를 `<section>`으로 한 겹 더 감싸면 B의 색은 무엇이 되는가. 변수를 찾아 올라가는 순서를 요소 이름으로 나열하시오.

> 예측 (2026-09-28): 탐색 순서 `id` → `section` → `zone`
>
> 실제: `[확인2] B --color-accent : #2f9e44`. 색은 초록 유지. 순서는 맞으나 **꼬리 2겹 누락**.
>
> 보강: 정확한 경로는 `div#inside` → `section` → `.zone` → `body` → `html`.
> `.zone`에서 멈추는 것은 거기서 **값을 찾았기** 때문이다. 못 찾으면 `body`를 거쳐 `html`까지 올라간다.
> `:root`(= `html`)에 변수를 모으는 이유가 이것이다. 경로의 종착지라 어디서 찾아도 반드시 닿는다.

확인 방법 (새로고침 후 Console):

```js
const b = document.querySelector('#inside');
const sec = document.createElement('section');
b.parentElement.insertBefore(sec, b);
sec.append(b);
console.log('[확인2] B --color-accent :', getComputedStyle(b).getPropertyValue('--color-accent'));
```

**핵심**: 한 겹을 더 감쌌는데 결과가 바뀌지 않는다. `section`에 선언이 없어 그냥 통과하기 때문이다.
탐색 기준은 **겹의 개수가 아니라 선언을 가진 가장 가까운 조상**이다.

## 4. `a5-flexbox.html` (Flexbox) -- ✅ 완료 2026-09-28 (Q1 정답 / Q2·Q3 오답 교정)

이 파일은 **예측 기록이 없습니다.** 파일을 열기 전에 아래 예측을 먼저 쓰십시오. 쓰지 않고 열면 관찰이 아니라 정답 확인이 됩니다.

### 예측 먼저 (파일 열기 전)

| 질문 | 예측 (2026-09-28, 파일 열기 전 기록) |
|---|---|
| Q1 `.nav`에만 `display:flex`를 걸었다. `.menu` 안의 `li` 3개는 가로로 나란히 놓이는가 | **세로로 쌓임** |
| Q2 `flex-direction: column` 인 상자에 `justify-content: center`를 주면 내용이 **가로**로 가운데 가는가 **세로**로 가는가 | **가로 가운데** |
| Q3 폭 400px 상자에 200px 칸 3개를 넣었다. `flex-wrap`이 없으면 칸의 실제 폭은 몇이 되는가 | **폭 200 유지, 2줄로 나뉨 (위 2칸 + 아래 1칸)** |

### 실험 1 · `display: flex`의 영향 범위 (Console 확인)

| 콘솔 줄 | 기대값 | 실제값 | 판정 |
|---|---|---|---|
| `[실험1] logo top / menu top` | 두 값이 **같다** | `323.15625 / 323.15625` | ✅ |
| `[실험1] li 1 / li 2 / li 3 top` | 세 값이 **서로 다르다** | `323.15 / 350.34 / 377.53` | ✅ |

**Q1 예측 적중.** 화면 관찰도 일치: LOGO와 메뉴는 나란히, 메뉴 항목 3개는 세로.
미션 연결: `.nav__menu`에 따로 `display: flex`를 걸어야 메뉴 항목이 가로로 펴진다.

읽는 법: `top`이 같으면 가로로 나란히, 다르면 세로로 쌓인 것입니다.
`display:flex`는 **직계 자식에게만** 적용됩니다. `.nav`의 자식인 `.logo`와 `.menu`는 나란히 서지만, `.menu`(ul)는 flex가 아니므로 그 안의 `li`는 그대로 세로로 쌓입니다.

### 실험 2 · 주축이 바뀌면 (Console 확인)

두 상자 모두 `flex-direction: column` + `justify-content: center`입니다. 차이는 `axis-b`에만 `align-items: center`가 있는 것뿐입니다.

| 콘솔 줄 | 기대값 | 실제값 | 판정 |
|---|---|---|---|
| `[실험2] axis-a 첫 상자 left / top` | left는 `0`, top은 0보다 큰 값 | `0 / 59.21875` | ✅ |
| `[실험2] axis-b 첫 상자 left / top` | left도 0보다 큰 값, top은 axis-a와 같다 | `882.5 / 59.21875` | ✅ |

**❌ Q2 예측 오답.** 예측은 "가로 가운데", 실제는 **세로 가운데**.

불일치 사유: 두 상자의 `top`이 59.21875로 **동일**하다. 이것이 `justify-content`가 세로를 움직였다는 증거다.
`axis-b`의 `left`가 882.5로 밀린 것은 `align-items: center` 때문이지 `justify-content` 때문이 아니다.

교정 규칙: `justify-content` = **주축**, `align-items` = **교차축**. 주축은 `flex-direction`이 가리키는 방향이다.
`row`면 주축이 가로, `column`이면 주축이 세로.
**"justify-content = 가로 정렬"로 외우면 `column`에서 반드시 틀린다. "주축 정렬"로 외운다.**

정리: `justify-content`는 **주축**을, `align-items`는 **교차축**을 다룹니다. `column`에서는 주축이 세로라서 `justify-content`가 세로를 움직입니다. 가로 정렬을 하려면 `align-items`가 필요합니다.

### 실험 3 · 공간이 부족할 때 (Console 확인)

> **참고 · flex 배지 찾는 방법** (관찰 중 막혔던 지점)
> 이 파일에서 `display: flex`가 걸린 요소는 `.nav`(실험1) · `.axis` 2개(실험2) · `.row` 2개(실험3)다.
> Elements 트리에서 `<nav class="nav">` 줄 오른쪽에 회색 `flex` 배지가 붙는다. 누르면 보라색 배치선이 겹쳐 보인다.
> 바로 아래 `<ul class="menu">` 줄에는 배지가 **없다.** 이것이 Q1의 눈으로 보는 증거다.

| 콘솔 줄 | 기대값 | 실제값 | 판정 |
|---|---|---|---|
| `[실험3] row-nowrap 칸1·2·3 폭` | 200이 아니라 **약 133** | `133.3` 전부 | ✅ |
| `[실험3] row-nowrap 칸1·2·3 top` | 세 값이 같다 (한 줄) | `1267.6875` 전부 | ✅ |
| `[실험3] row-wrap 칸1·2 폭 / top` | 폭 200, top 같음 | `200.0 / 1358.0625` | ✅ |
| `[실험3] row-wrap 칸3 top` | 칸1·2보다 **큰 값** (다음 줄) | `200.0 / 1389.25` | ✅ |

**❌ Q3 예측 오답.** 예측은 "폭 200 유지, 2줄(위 2칸 + 아래 1칸)".

불일치 사유: 예측한 내용은 **`row-wrap`의 결과**다. `flex-wrap: wrap`을 넣었을 때만 그렇게 된다.
`flex-wrap` 기본값은 `nowrap`이라 줄을 바꾸지 않는다. 대신 flex 아이템의 기본값 `flex-shrink: 1` 때문에
자리가 부족하면 지정한 `width`를 **스스로 줄인다**. 400 ÷ 3 = 133.3.

교정 규칙: **flex 안에서 `width: 200px`은 약속이 아니라 희망값이다.**
줄이지 않으려면 `flex-shrink: 0`, 다음 줄로 넘기려면 `flex-wrap: wrap`을 명시해야 한다.

정리: flex 아이템은 기본값 `flex-shrink: 1`을 가지므로, 자리가 부족하면 지정한 `width`를 **스스로 줄입니다.** `width: 200px`이 약속이 아니라 희망값인 셈입니다. 줄이지 않고 다음 줄로 넘기려면 `flex-wrap: wrap`이 필요합니다.
