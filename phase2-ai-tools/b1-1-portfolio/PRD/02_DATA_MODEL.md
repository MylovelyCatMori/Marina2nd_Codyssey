# B1-1 나를 소개하는 웹페이지 -- 데이터 모델

> 이 프로젝트에는 **데이터베이스가 없다.** GitHub Pages는 정적 호스팅이라 서버가 없기 때문이다.
> 따라서 여기서 말하는 "데이터 모델"은 세 가지다.
> ① 브라우저 메모리에 사는 **상태 객체** ② 외부에서 받아오는 **API 응답 모양** ③ 브라우저에 남기는 **localStorage 값**

---

## 전체 구조

```
                         [GitHub API]  (외부, 읽기 전용)
                              |
                        fetch (1회 or 재시도)
                              ↓
   [localStorage] ---> [ AppState ] <--- [사용자 이벤트: click / input / submit / scroll]
    (테마만 영속)            |
                             | render()
                             ↓
                          [ DOM 화면 ]

   AppState 내부:
     ├── theme          (문자열)          --1:1--> localStorage['theme']
     ├── repoState      (객체)            <--N-- GitHubRepo (배열)
     ├── activeLanguage (문자열)          -- repoState.data에서 파생
     ├── formValues     (객체)
     ├── formErrors     (객체)
     └── uiState        (객체: 메뉴/스크롤)
```

**핵심 원칙: 단방향.** 이벤트가 상태를 바꾸고, 상태가 화면을 그린다. 화면이 상태를 바꾸는 역방향은 없다. React를 배우기 전에 이 방향성을 손으로 만들어보는 것이 미션의 목적이다.

## 엔티티 상세

### 1. AppState -- 앱 전체 상태

화면을 결정하는 모든 값을 담는 하나의 객체. 흩어놓지 않고 한곳에 모으는 이유는 "지금 화면이 왜 이렇게 보이는가"를 한 곳만 보면 알 수 있게 하기 위해서다.

| 필드 | 설명 | 예시 | 필수 |
|---|---|---|---|
| theme | 현재 테마 | `'dark'` | O |
| repoState | GitHub 저장소 취득 상태 | 아래 2번 참조 | O |
| activeLanguage | 선택된 언어 필터 | `'Python'` | O |
| formValues | 폼 입력값 | 아래 4번 참조 | O |
| formErrors | 폼 에러 메시지 | 아래 5번 참조 | O |
| uiState | 메뉴 열림/스크롤 위치 파생값 | 아래 6번 참조 | O |

### 2. repoState -- 저장소 취득 상태 (이 프로젝트의 심장)

"데이터"와 "데이터를 가져오는 과정"을 한 객체로 묶는다. 로딩 중인지, 실패했는지, 성공했는데 비었는지를 **하나의 `status` 문자열**로 표현한다.

| 필드 | 설명 | 예시 | 필수 |
|---|---|---|---|
| status | 현재 어느 상태인가 | `'loading'` | O |
| data | 성공 시 저장소 배열 (원본, 절대 변형 금지) | `[{...}, {...}]` | O (기본 `[]`) |
| error | 실패 시 사용자에게 보여줄 메시지 | `'프로젝트를 불러올 수 없습니다'` | X (기본 `null`) |

**status가 가질 수 있는 값 4가지** (요구사항 F-50~F-53에 1:1 대응)

| status | 화면 | 언제 | 요구사항 |
|---|---|---|---|
| `'loading'` | 스피너 또는 "로딩 중..." | fetch 시작 직후 | F-50 |
| `'success'` | 카드 리스트 | 응답 OK + 배열 길이 > 0 | F-51 |
| `'error'` | "프로젝트를 불러올 수 없습니다" + **[다시 시도]** | 네트워크 실패 / 403 레이트 리밋 / 404 | F-52, F-55 |
| `'empty'` | "표시할 프로젝트가 없습니다" | 응답 OK + 배열 길이 === 0 | F-53 |

> **왜 `'empty'`를 `'success'`와 분리했나** -- 데이터가 0개인 것은 **실패가 아니라 성공**이다. 에러로 처리하면 "다시 시도" 버튼을 눌러도 영원히 0개다. 사용자를 헛수고시키게 된다.
>
> **왜 `isLoading` 같은 boolean 여러 개를 쓰지 않았나** -- boolean 3개면 조합이 8가지인데, 그중 실제로 존재할 수 있는 건 4가지뿐이다. "로딩 중이면서 동시에 에러"라는 불가능한 상태가 코드상 표현 가능해지면 언젠가 그 버그가 난다. 문자열 하나면 애초에 4가지 외에는 만들 수 없다.

### 3. GitHubRepo -- API 응답 항목

`https://api.github.com/users/MylovelyCatMori/repos` 가 배열로 돌려주는 객체. **응답에는 필드가 80개 넘게 들어있지만 우리가 쓰는 건 아래뿐이다.** 구조분해 할당(F-44)으로 필요한 것만 꺼낸다.

| 필드 | 설명 | 예시 | 화면에서 |
|---|---|---|---|
| id | 저장소 고유 번호 | `123456789` | 카드 key |
| name | 저장소 이름 | `Marina2nd_Codyssey` | 카드 제목 |
| description | 저장소 설명 | `코디세이 학습 저장소` | 카드 본문 (**null일 수 있음**) |
| html_url | 저장소 웹 주소 | `https://github.com/...` | 카드 링크 |
| language | 주 언어 | `Python` | 배지 + 필터 기준 (**null일 수 있음**) |
| stargazers_count | 스타 수 | `5` | 카드 하단 |
| forks_count | 포크 수 | `2` | 카드 하단 |
| updated_at | 최종 수정 시각 | `2026-09-01T10:00:00Z` | 정렬 기준 |

> **null 주의 (실제로 터지는 지점)** -- `description`과 `language`는 **자주 null이다.** 새로 만든 저장소, README만 있는 저장소가 그렇다. 템플릿 리터럴에 그대로 넣으면 화면에 문자열 `null`이 찍힌다. 카드 렌더링 시 기본값 처리 필수.
>
> **language가 null인 저장소의 필터 처리** -- `'Unknown'` 같은 기본 라벨로 묶는다. 그냥 두면 어떤 필터를 눌러도 나타나지 않는 유령 카드가 된다.

### 4. formValues -- 폼 입력값

| 필드 | 설명 | 예시 | 필수 |
|---|---|---|---|
| name | 보내는 사람 이름 | `홍길동` | O |
| email | 회신받을 이메일 | `hong@example.com` | O |
| message | 문의 내용 | `포트폴리오 잘 봤습니다` | O |

### 5. formErrors -- 폼 에러 메시지

`formValues`와 **같은 키를 갖는 짝 객체.** 빈 문자열이면 에러 없음.

| 필드 | 검증 규칙 | 에러 메시지 예시 | 요구사항 |
|---|---|---|---|
| name | 공백 제거 후 길이 > 0 | `이름을 입력해 주세요` | F-38 |
| email | 공백 제거 후 길이 > 0 **그리고** 이메일 형식 | `이메일 형식이 올바르지 않습니다` | F-38, F-39 |
| message | 공백 제거 후 길이 > 0 | `메시지를 입력해 주세요` | F-38 |

> **키를 일치시킨 이유** -- 필드 이름만 알면 값과 에러를 같은 방식으로 찾을 수 있다. 검증 함수가 필드마다 따로 있을 필요가 없어진다.
>
> **검증 순서 주의** -- 빈 값 검사가 형식 검사보다 **먼저**다. 빈 칸에 "이메일 형식이 올바르지 않습니다"라고 뜨면 사용자는 무엇이 틀렸는지 모른다.

### 6. uiState -- 화면 조작 상태

| 필드 | 설명 | 예시 | 트리거 | 요구사항 |
|---|---|---|---|---|
| isMenuOpen | 모바일 햄버거 메뉴가 열려 있는가 | `false` | 버튼 click | F-30 |
| isScrolled | 스크롤이 **60px**을 넘었는가 | `true` | scroll | F-33 |
| showTopButton | 스크롤이 **300px**을 넘었는가 | `true` | scroll | F-32 |

> **임계값 3종은 README에 반드시 명시** (F-32, F-33, F-36 요구). 상수로 뽑아 코드 상단에 모은다. 매직 넘버 금지.

## localStorage 저장 항목

브라우저에 남는 유일한 값.

| 키 | 값 | 언제 쓰나 | 없으면 |
|---|---|---|---|
| `theme` | `'light'` 또는 `'dark'` | 토글할 때마다 저장, 페이지 로드 시 복원 | `prefers-color-scheme`로 시스템 설정을 따름 (보너스 B-04) |

**테마 결정 우선순위** (보너스 B-04 채택으로 인해 규칙이 필요해짐)
```
1순위: localStorage['theme']         -- 사용자가 직접 고른 값
2순위: prefers-color-scheme 미디어쿼리 -- OS 설정
3순위: 'light'                        -- 최종 기본값
```
> **왜 localStorage가 1순위인가** -- 사용자가 명시적으로 선택한 것이 OS 기본 설정보다 항상 우선한다. 반대로 하면 사용자가 다크모드를 껐는데 새로고침하면 다시 켜지는 황당한 동작이 된다.

**폼 입력값을 저장하지 않는 이유** -- 남의 컴퓨터에 남는다. 개인정보이고, 요구사항에도 없다.

## 왜 이 구조인가

- **단순성**: 상태를 6개 필드로 제한했다. 과제 요구는 "상태→렌더링 흐름 3개 이상"인데 이 구조로 4개(테마/저장소/폼/필터)가 자연히 나온다
- **확장성**: React를 배우면 `AppState`의 각 필드가 그대로 `useState` 하나씩이 된다. 지금 구조를 그대로 옮길 수 있다
- **불변성**: `repoState.data`는 원본이며 절대 변형하지 않는다. 필터 결과는 `filter()`가 만든 **새 배열**이다. 원본을 잘라내면 "전체"로 되돌아갈 방법이 사라진다
- **불가능한 상태를 만들 수 없게**: `status` 문자열 하나로 4가지 화면을 대표시켜, "로딩이면서 에러"같은 모순 상태를 구조적으로 차단했다
